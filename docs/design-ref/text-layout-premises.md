# 文章とレイアウトの大前提（2026-10-27）

文字・枠・文を別々に直してループした反省から、調べて決めた大前提。どの画面も、この順番と決まりに沿って作る。clarity-rules.md（遊びの4点）・typography.md（文字の段）はこの下に置く。

## 0. 作る順番（入れ替えない）
1. **中身**：その画面で伝えること（遊びの4点・押すと何が起きるか・判断の材料）を決める。
2. **優先順位**：中身に番号を付ける。1番は1つだけ（一番目立たせる物）。
3. **表し方**：1つずつ「絵（形・色・印・札）」「数字」「文」のどれで見せるかを決める。絵で見せられる物は絵にする。
4. **文字の大きさ**：文で残った物にだけ、役目の段を当てる（type-roles.css）。
5. **枠**：1〜4が入るように枠を決める。動かしてよいのは枠の側。

## 1. 文章の大前提
1. **文は3種類だけ**：相手の言葉（台詞・心の声・手がかりの文）／今やること（1行）／リコ先輩の一言（判断の目安が要る時だけ）。遊びの4点は初回とルールの札にだけ出す。
2. **意味を削って収めない。** 入らない時は、絵にする・段を分ける・枠を変える。文を短くするのは、同じ意味をもっと分かりやすく言える時だけ。
3. **1行は15字前後、2行まで**を目安にする（大きい字では1行15字が読みやすく、20字で評価が下がったという研究がある）。
4. ゲームの普通の言葉で書く。作った言葉・中の名前を出さない（clarity-rules.md の3）。
5. **太さ**：太くするのは見出しと押す所だけ。読ませる文（台詞・手がかり）は太くしすぎない（太い明朝の大きな文字が狭い枠で塊に見えた）。

## 2. レイアウトの大前提
1. **一番大事な物が一番目立つ**：大きさ・位置・明暗・強さで優先順位を見せる。全部が同じ強さだと、少ない情報でも読み取りが遅くなる。
2. **一目で分かる**：細かい所ではなく、形と明暗で伝える。判断の材料は1つの絵にまとめる（天秤・棒と線）。
3. **要る時だけ出す**：その段で要らない物は出さない（終わった手順・まだ先の材料）。
4. **押す所**：44pt（Apple）／48dp（Google）以上、押す所どうしの間は8以上。親指の届く下の段に置く。
5. **実寸で見る**：決める時は、実際の端末の大きさの画面（844×390・667×375・1280×800）で、手本と前の版と並べて目で見る。

## 3. 文字の大きさの大前提
1. 下限は14px（2026-10-21 ユーザー指摘「小さくて読めない、拡大できない」）。
2. 役目の段で書き、同じ役目は全画面で同じ大きさ。決め所は type-roles.css の1か所。
3. 段の数字は、表し方（0の3）が決まった画面で、今・案・前の比べ絵を撮り、ユーザーに選んでもらって1回だけ決める。アプリの本文17pt（縦向きで文章を読む時の標準）を、狭い枠のゲームにそのまま当てない。

## 4. 見せる前の確かめ（3つ）
1. 役目のそろい：同じ役目が全画面で同じ大きさか（qa/typeaudit.mjs）。
2. 下限・はみ出し・切れ・巻き取り（qa/readaudit.mjs の QA_MEASURE、qa/fontlint.mjs）。
3. 実寸の画面を、手本と前の版と並べて目で見る。1と2が0でも、3を通らなければ見せない。
直しは決めた後に全画面へ一度に当て、撮影と配信は1回にする。

## 5. 見落としを防ぐための決まり（2026-10-27 見直しで足した）
| 見落とし | 起きた直し | 決まり |
|---|---|---|
| 画面の範囲 | 読み合いだけ直すと卓・結果・ホーム・交換所・物語とずれる | 大前提は全画面に一度に当てる。一部だけ先に配信しない |
| 場面の違い | 初回／2回目、装備あり（クリア後のセーブ）、フィーバー中、答え合わせの崩れを後から見つけた | 画面ごとに起こりうる場面を全部書き出し、全部を撮る |
| 文の長さの最大 | 作られる文の一番長い物で折れた・はみ出した | 文の元の一覧から一番長い物を数え、枠はその長さで決める |
| 実機の安全域 | iPhone の切り欠き・下のバー | 安全域を引いた大きさで枠を決め、iPhone 16e の大きさでも撮る |
| 重なり | カットイン・吹き出し・小窓が文字や押す所を隠した | 重なる物の出る時と場所も表に書いて確かめる |
| 決めることの後出し | 見せるたびに別の直しが出た | ユーザーに決めてもらうこと（大きさ・文言・絵）は作り直しの前にまとめて1回で聞く |
| 検査の道具の壊れ | 検査が壊れて「全部0」と出た | 使う前に、わざと崩した画面で道具が見つけられるかを確かめる |

### 確定した順序
1. 全画面の「中身・優先順位・起こりうる場面・文の一番長い物」の表を作る（docs/design-ref/screen-inventory.md）
2. 絵か文かを全部決める
3. ユーザーに決めてもらうことを1回にまとめて見せる（文字の段の比べ絵・変える文言）
4. 決まった物で全画面を一度に作り直す
5. 全場面を全部の大きさ（844×390・667×375・iPhone 16e・1280×800）で1回だけ撮り、4の3つの確かめをして配信する
3の後に本体の側から直しが出たら、表の書き漏らしなので、表に足してから直す。その場しのぎの直しはしない。

## 6. 既存の作り手の解き方から足した決まり（2026-10-27 調べもの）
同じ悩み（文・枠・大きさを直すたびに崩れる）は、翻訳の現場とゲームの UI の作り手の間でよく知られていて、解き方がある。
1. **枠に3割の余裕**：決めた文が3割長くなっても入る枠にする（翻訳の現場では2〜4割の伸びを見込むのが普通）。文を少し直しても枠の直しが要らない。
2. **枠ごとの字数の上限を最初に決める**：ボタン・吹き出し・今やること・欄の1行ごとに上限を表に書き、文の字数を数える検査で見張る（後回しにすると崩れる）。
3. **文を1か所に集める**：書き直す時に、どこに出て何字まで入るかが分かるようにする。
4. **わざと3割長くした文で先に崩れを探す（擬似翻訳）**：作り直しの最初に、全部の文を自動で3割長くして撮る（Godot のエンジンにもある方法）。崩れはお見せする前に機械で見つける。
5. **大きさは役目の名前で持つ**（type-roles.css）。
6. **ほかのゲームと並べて見直す**（グリーの社内の取り組み）。区切りごとに、手本と並べた比べ絵を作る。
7. スマホの文字の目安は本文14〜16px・説明12〜14pxという記事が多い（本文17pxは狭い枠のゲームには大きい）。
